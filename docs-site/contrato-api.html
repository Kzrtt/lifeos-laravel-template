Contrato da API

O front HTML/JS foi copiado byte a byte do LifeOS original; o backend fala exatamente o contrato que ele já esperava. Não há SPA a construir: este contrato é o que o front usa.

✅ implementado

Forma da chamada

POST /functions/v1/lifeos-<módulo>
Content-Type: application/json

{ "token": "<senha>", "action": "query | create | update | delete | …", …campos }

200  → { "ok": true, …dados }
4xx  → { "ok": false, "error": "codigo_curto" }
  1. O mesmo contrato vale para todo módulo: uma rota por módulo, a operação vem em action.
  2. token vai no corpo, não em header. 401 / unauthorized quando a senha não confere; o gate de cada página no front é só UX — a fronteira real é o servidor.
  3. Erros de negócio são códigos curtos em error (has_tarefas, nome_duplicado…), que o front traduz em mensagem; nunca texto livre.
  4. Os vocabulários (tags, status) são validados no servidor contra a tabela lifeos_vocabularios.
  5. O endpoint do MCP é a exceção: o token vai no path (/functions/v1/lifeos-mcp/<token>), porque conectores pessoais do claude.ai não aceitam header estático.
  6. Compatibilidade de RPC: POST /rest/v1/rpc/check_page_access mantém o formato antigo.
